Курсова робота з дисципліни «Вебтехнології та розробка вебзастосувань» (ОІ-31, НУ «Львівська політехніка», 2026).

## 1. Що будуємо

**Тема:** вебсистема розрахунку собівартості та планування черги виконання індивідуальних замовлень для локальної майстерні (3D-друк, лазерна порізка, столярка).

**Проблема:** малі майстерні довго рахують складні замовлення вручну і зривають дедлайни, бо не враховують час налаштування обладнання (setup / changeover).

**Рішення (дві ядрові алгоритмічні задачі):**
1. **Калькулятор собівартості та ціни** замовлення з багатьох позицій.
2. **Планувальник черги** на кількох верстатах з урахуванням часу переналаштування, робочого календаря та дедлайнів + перевірка «чи встигну прийняти нове замовлення до дати X».

Це НЕ базовий CRUD. Оцінюється власна бізнес-логіка, яку студент мусить обґрунтувати в розділі 2.2 записки і захистити на комісії.

## 7. Специфікація алгоритмів (ядро проєкту)

### 7.1 Собівартість позиції замовлення (`domain/pricing.js`)

Для позиції з кількістю `q`:

```
material  = q · usage · pricePerUnit · (1 + wastePct)
machine   = q · runTimeH · machine.hourlyRate        # у ставку входять амортизація + електрика (kW · тариф)
setup     = setupTimeH · laborRate / batchShare        # setup ділиться на партію, якщо матеріал той самий
labor     = (prepH + postProcessH) · laborRate
base      = material + machine + setup + labor
withRisk  = base / (1 − failureRate)                   # брак (особливо 3D-друк)
cost      = withRisk · (1 + overheadPct)
price     = cost · (1 + marginPct) · (1 + rushSurcharge) · (1 − volumeDiscount(q)) · (1 + taxPct)
```
Параметри (ставки, %, пороги знижок, rush-коефіцієнти) — в таблиці `settings`, редагуються в UI. Повертай **розбивку по складових** (для UI та звіту). Перевірка вхідних даних через Zod.

### 7.2 Час переналаштування (`domain/setup.js`)

```
setup(prev, next, machine) =
    base[machine.type]
  + materialChange[prev.material → next.material]   # матриця; 0 якщо той самий
  + colorChange   (якщо інший колір/полотно/лак)
  + toolChange    (сопло/фреза/лазерна лінза)
  + warmup        (якщо prev == null, тобто перша робота зміни)
```
Матриця переналаштувань зберігається в БД (`setup_rules`) з дефолтами в seed.

### 7.3 Планувальник (`domain/scheduler.js`)

Задача: `m` верстатів, `n` робіт; кожна робота має час виконання `p_i` (залежить від верстата), дедлайн `d_i`, пріоритет `w_i`, список допустимих верстатів, час переналаштування `s_ij`, залежний від послідовності. Верстати працюють за календарем змін (години/вихідні).

Реалізуй **list scheduling** з правилами (обирається в UI, для порівняння):
- `FIFO`, `EDD` (earliest due date), `SPT` — базові;
- **`ATCS`** (Apparent Tardiness Cost with Setups, Lee & Pinedo) — основний:
  `I_i(t, prev) = (w_i / p_i) · exp(−max(d_i − p_i − t, 0) / (k1 · p̄)) · exp(−s(prev,i) / (k2 · s̄))`
  `k1`, `k2` — налаштовувані (дефолт 2 і 0.5). На кожному кроці вільний верстат бере роботу з максимальним індексом.

Вихід: для кожної роботи `machineId, start, end, setupStart, setupEnd, lateness`; метрики: кількість запізнень, сумарне запізнення, сумарний час setup, завантаження верстатів, makespan. Підтримай **закріплені (locked) роботи**, які планувальник не рухає.

**Порівняння стратегій:** endpoint повертає метрики для FIFO/EDD/SPT/ATCS на тих самих даних → графік у UI і таблиця в розділі 3.4.

### 7.4 Feasibility / «чи встигну» (`domain/feasibility.js`)

`POST /api/quotes/feasibility`: беремо поточний план + гіпотетичне нове замовлення → перепланування на копії → відповідь: `earliestFinish`, `meetsDeadline`, список замовлень, що зсунулись/запізнились, рекомендована rush-націнка. Нічого не пишемо в БД.

### 7.5 Клієнтські алгоритми (`client/src/lib/`)

- Розкладка діаграми Ганта (масштаб часу → піксельні координати, пакування по доріжках).
- Перевірка конфліктів при ручному перетягуванні роботи (перетин, вихід за календар, недопустимий верстат) до відправки на сервер.
- Дебаунс-прев'ю ціни у формі замовлення (запит `/api/pricing/preview`) + локальна валідація.
